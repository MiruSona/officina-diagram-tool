## 결론

### 가장 중요한 발견 — 2D 타일 기반이라 텍스트로 공간 배치까지 그려진다

앞서 "AI는 2D 배치를 못 그린다"고 봤는데, **횡스크롤 게임에서는 사정이 다르다.**

> **타일 그리드를 문자로 찍으면 발판·낭떠러지·적 위치가 정확한 좌표로 표현된다.**
> 3D였다면 불가능했을 것이 **2D 타일 기반이라 가능하다.** 이게 이 프로젝트의 핵심 기회다.

한 화면이 40×23 타일 수준이면 문자 그리드로 충분하다. 픽셀 단위 정밀도가 필요해지는 순간에만 무너진다.

### 진짜 필요한 도면은 7개

| 순위 | 도면 | 왜 |
| --- | --- | --- |
| **1** | **룸 타일맵 스케치** (지형·발판·적·아이템·체크포인트를 한 장에) | 실제 개발사가 제일 먼저 그리는 것. **나머지 레벨 도면 대부분을 흡수한다** |
| **2** | **이동 기준선 표** (점프 높이·거리를 **타일 수**로) | 1번의 좌표계가 된다. 이게 없으면 1번이 의미 없다 |
| **3** | **공격 타임라인** (선딜/지속/후딜) | 액션 전투 설계의 유일한 진짜 "그림". **표로는 관계가 안 보인다** |
| **4** | **상태 전이도** (플레이어 이동 / 적 AI / 보스 페이즈) | **형식 하나로 3가지 용도.** 코드와 1:1 대응 |
| **5** | **진행 구조 그래프** (스테이지 흐름, 잠금-열쇠) | 메트로배니아식 구조가 있으면 필수. 없으면 표로 충분 |
| **6** | **구간 페이싱 표** | **곡선 그래프가 아니라 표가 실제 형식** |
| **7** | **화면 흐름도** | 한 번 그리고 끝. 싸다 |

### 만들지 말 것 (과투자)

**점프 아크 곡선 그래프 · 난이도 곡선 그래프 · 정밀 히트박스 도형 · 콤보 트리 · 카메라 전용 도면**

## 2. 텍스트로 되는 것 / 안 되는 것

### 완전히 가능

- 순서·분기·상태·전이 → 순서도, 상태도, 노드-엣지
- 시간 구간 → 프레임 타임라인 (문자 막대)
- 수치 → 표
- **공간 배치까지 가능** ← 2D 타일이라서

### 불가능 (이미지·에디터여야 함)

- 히트박스가 스프라이트의 **어느 부분을 덮는지** (픽셀 단위 모양·오프셋)
- 곡선의 실제 생김새 (점프 궤적의 미묘한 형태)
- 아트·연출 의도
- **"느낌"** — Yacht Club은 이걸 문서 대신 **GIF**로 남긴다

### 경계선

타일 해상도가 거칠면 텍스트 그리드로 충분. 픽셀 정밀도가 필요해지면 무너진다.

## 3. 근거

### 3-1. 실제 제작 순서 — Yacht Club Games (Shovel Knight)

*Specter of Torment* 레벨 제작 5부작이 공개돼 있다. 실제 순서:

1. 레벨 테마 후보를 **스프레드시트**에 모아 승인
2. **초기 러프 스케치** — "왼쪽에 넣어야 할 오브젝트 목록, 오른쪽에 구간별 아주 거친 그림"
3. **상세 마크업** — 기존 방을 X로 지우고 새 경로를 그림. 체크포인트·비밀방·아트 메모를 덧씀
4. 이 마크업이 **"최종 레이아웃과 그리 멀지 않다"**

방을 **"전투 방 / 플랫포밍 방"** 으로 분류해 비율을 맞춘다. 도구는 **"디지털이든 종이든"** 상관없다고 명시.

2부의 명언:

> **"레벨 레이아웃은 공간 관리 프로젝트다. 재미있는 상황을 떠올리는 게 10%, 간격 요구사항과 씨름하는 게 90%다."**

3·4부는 도면이 아니라 **"패스(pass)" 단위 반복 작업**이 중심이다 (블로커 패스, 스피드러너 패스, 배경 아트 패스, 화면 흔들림 패스). 골드 총량 밸런싱은 **스프레드시트 도구**를 따로 만들어 썼다.

### 3-2. 레이아웃 그리기 표준 5단계 (Level Design Book)

**파르티 썸네일**(30초짜리 러프 5~10장) → **버블 다이어그램**(방=타원, 연결=화살표, 최소 3안) → **평면도** → 아이소메트릭(높이가 복잡할 때만) → **게임플레이 마크업**(주 경로, 스폰, 목표, 의도 주석)

> 원칙 : **"우리는 건축가가 아니다. 플레이어 경험을 상상하는 데 필요한 최소한만 그려라."**

### 3-3. 점프 거리는 "타일 수"로 쓴다 — 이게 설계 언어다

- Level Design Book은 **플레이어 메트릭**(물리적 사실)과 **빌딩 메트릭**(설계 가이드라인)을 구분한다. *Psychonauts 2*는 **에디터에 점프 궤적 미리보기**를 넣어 편집 중 도달 가능 여부를 보여줬다
- *Super Mario Bros.* 1-1 분석 : **"모든 발판은 지면에서 4블록 또는 8블록 위에 있다"**, "마리오의 가장 긴 점프는 거의 정확히 4블록 높이에 도달한다"
- 역공학 GDD도 같은 말 : "모든 구덩이는 대략 마리오가 뛸 수 있는 길이이고, 위쪽 구조물은 모두 닿을 수 있는 높이다"

> 경고도 있다 — **"메트릭은 유용하지만 마법은 아니다."**

### 3-4. 레벨 구조에는 학술 표기법이 있다 (Smith, Cha, Whitehead)

*A Framework for Analysis of 2D Platformer Levels* (UC Santa Cruz)

- 구성요소 5종 : **platform / obstacle / movement aid / collectible / trigger** (구덩이도 obstacle)
- 계층 : **레벨 > 셀(선형 구간) > 리듬 그룹**, 셀들은 **포털**로 연결
- **리듬 그룹** = 겹치지 않는 짧은 도전 묶음. 음악의 악구처럼 시작·중간·끝이 있다. 그룹 사이가 곧 **쉬는 구간(rest area)** 이고 세이브 포인트나 보상이 놓인다
- **"긴 액션 뒤 쉴 틈이 없으면 플레이어가 실수한다."**

**이게 중요한 이유** : 논문은 스크린샷 위 사각형으로 표시했지만, 텍스트에서는 **"구간 목록 + 각 구간의 도전 종류 + 쉼터 표시"** 로 **무손실 변환된다.**

### 3-5. 난이도 페이싱은 곡선이 아니라 표다

실제 사례:
- **비트 시트** — 세트피스·장면·보스전을 카드로 적고 재배열 (Trello, Notion, 인덱스카드)
- **강도 그래프** — 비트마다 0~5점을 매겨 시간축에. **난이도가 아니라 몰입도**를 잰다
- *God of War Ragnarök* 의 **"boss flow" 문서**
- **Valve** 는 *Half-Life 2: Ep2*, *Left 4 Dead* 에서 비트를 Explore / Combat / Choreo / Puzzle 로 분류
- *Journey* 는 여러 경험 목표를 강도 막대로 추적하는 **스프레드시트**

난이도 곡선 자체에 대해서는 실무자가 **"매끄러운 상승 곡선"을 부정**하고 **"난이도 톱니(Difficulty Saw)"** 를 제안한다 — 새 기능을 넣으면 난이도가 떨어졌다가 숙달되며 오른다.

> **"전용 소프트웨어는 없다."** 대신 사망 위치 추적, 레벨별 클리어율, 플레이테스터 스프레드시트를 쓴다.

**단서 : 이 문서들은 개발 중에 대부분 낡는다.**

### 3-6. 메트로배니아 잠금-열쇠 — 학술 표준이 있다

Dormans, *Adventures in Level Design*. 핵심은 **미션과 공간을 분리**하는 것:

- **미션** = 해야 할 일의 그래프. 알파벳은 `key`, `lock`, `room`, `monster`, `treasure`. 규칙 예: `obstacle → key + obstacle + lock + obstacle`
- **공간** = 실제 배치. 방=노드, 통로=엣지
- **같은 미션이 여러 공간에 매핑될 수 있다**

GMTK의 Boss Keys 던전 그래프와 같은 형식이다. **텍스트로 완벽히 그려진다.**

### 3-7. 카메라는 도면이 아니라 "용어 라벨"이다

Itay Keren의 *Scroll Back* 이 사이드스크롤러 카메라 기법 25종 이상에 이름을 붙여 사실상 표준 용어집이 됐다 — position-locking, edge-snapping, **camera-window**, lerp-smoothing, platform-snapping, **dual-forward-focus**, target-focus, **cue-focus**, **region-focus**, camera-path 등.

표현 방식은 정식 다이어그램이 아니라 **주석 붙인 스크린샷/GIF** 다.

> **실무 결론 : 카메라 도면을 그릴 게 아니라 구간마다 "이 방은 region-focus + edge-snapping" 식으로 라벨을 붙이면 된다.**

### 3-8. 적 배치는 표 + 매트릭스

역할(Grunt / Squad / Leader / Tank / Swarm / Sniper) × 속성(속도, 체력, 사거리, DPS) **스프레드시트**로 로스터의 빈틈을 본다. 추가로 **직교 축 매트릭스**(x축: 물러남 vs 돌진, y축: 투사체 vs 히트스캔)로 적들이 서로 다른 자리를 차지하는지 확인.

초기엔 숫자 대신 **"낮음/중간/높음"** 으로 쓰라고 권한다 — 어차피 프로토타이핑에서 크게 바뀐다.

### 3-9. 프레임 데이터는 격투게임 전용이 아니다

디자이너 Celia Wagar의 글 제목이 그대로 답이다 — *Frame Data Patterns that **ALL Game Designers** Should Know*.

| 구간 | 정의 |
| --- | --- |
| **Startup** | 애니메이션 시작부터 첫 히트박스 나타나기 전까지 |
| **Active** | 히트박스가 존재해 때릴 수 있는 구간 |
| **Recovery** | 히트박스 사라진 뒤 새 입력을 받기 전까지 |

파생 : hitstun, blockstun, **프레임 유불리**, 콤보(link), 캔슬, frame trap, unsafe, pushback

**격투게임이 아닌 사례**도 든다 — *Metal Gear Solid* 의 1-2-3 콤보가 프레임 유리가 과해서 무한 콤보가 된 버그.

설계 팁 : **"먼저 원하는 대로 콤보가 이어지게 만들고, 그 다음에 각 기술의 후딜을 조절해서 프레임 유불리를 정하라."**

### 3-10. 프레임 데이터는 두 형태로 존재한다

- **표** — 격투게임 위키(Dustloop, SuperCombo)가 기술별 startup/active/recovery를 표로 관리. **밸런스를 볼 때는 표**
- **타임라인** — 실제 엔진 작업에서는 **애니메이션 타임라인 위의 구간**으로 저작. Unreal의 **Anim Notify State** 가 정확히 이것. 시작·끝을 드래그해 **구간**을 만들고 start/update/end 이벤트를 준다. **대표 용도가 "공격 애니메이션 중 무기 콜리전을 켜고 끄는 것"**

> **판단 : 타임라인은 실제로 쓰인다.** 문서에서는 프레임 축 위 문자 막대가 표와 타임라인을 동시에 만족시킨다. 여러 기술을 세로로 쌓으면 상호 유불리도 눈에 보인다.

### 3-11. 히트박스는 텍스트로 못 그린다 — 대신 안 그려도 된다

- 실무 표현은 **에디터/디버그 오버레이 도형**
- Sonic 물리 문서조차 히트박스는 **폭/높이 반값 숫자**로 기술
- 문서에 남길 값 : 사거리(px 또는 타일), 히트박스 크기(가로×세로), 캐릭터 기준 오프셋, 지속 프레임

> **모양·위치를 그려야 하는 순간이 오면 그건 문서가 아니라 게임을 켜서 볼 일이다.**

### 3-12. 점프 아크는 종이에 그리지만 산출물은 숫자 4개다

J. Kyle Pittman, GDC 2016 *Math for Game Programmers: Building a Better Jump*. 동기 슬라이드:

> "하드코딩과 추측 게임을 피하자 / **점프 궤적을 종이에 설계하고** / 그 점프를 코드로 모델링할 상수를 유도하자"

방법:
- 포물선을 **정점 높이 `h`** 와 **정점까지 시간 `t_h`** 로 → `v₀ = 2h/t_h`, `g = −2h/t_h²`
- 시간축 대신 **거리축**으로 다시 그린다 (레벨 설계에 맞게). **정점까지 수평거리 `x_h`** 와 **수평속도 `v_x`** → `v₀ = 2h·v_x/x_h`, `g = −2h·v_x²/x_h²`
- 가변 높이 점프 / 빠른 낙하 / 더블 점프는 **"서로 다른 모양의 포물선 조각을 이어 붙이는 것"**

> **판단 : 곡선 그래프는 "가변 점프·더블 점프를 왜 이렇게 쪼갰는지" 설명할 때 1회만 필요하다.**
> 평소 문서에는 `h`(타일 수), `x_h`(타일 수), `v_x` 세 값이면 곡선이 완전히 결정된다.

### 3-13. 물리 파라미터는 표다

Sonic Retro의 *Sonic Physics Guide* 가 이 장르 최고 공개 물리 문서인데, 형식이 일관되게 **상수 표 + 산문 + 의사코드**다. **곡선 그래프는 없다.**

| 상수 | 값 |
| --- | --- |
| `acceleration_speed` | 0.046875 |
| `deceleration_speed` | 0.5 |
| `friction_speed` | 0.046875 |
| `top_speed` | 6 |

문서 스스로 **"엔진 무관하게 기술한다"** 고 선언하고 Unity/Godot/GameMaker에 옮길 수 있게 썼다.

### 3-14. 2D 횡스크롤 GDD 목차 표본

역공학이지만 *Super Mario Bros.* 디자인 문서화의 목차가 좋은 표본이다.

내용을 보면 — 점수는 **적 × 처치방법 표**, 적 AI는 **적 × 행동 × 이동 표**, 스테이지는 **World-Area 트리 표**, 화면 흐름은 **순서도**, **레벨 레이아웃만 부록에 이미지로 뺀다.**

> **즉 이미지가 꼭 필요한 건 레벨 레이아웃 하나뿐이다.**

| 형식 | 쓰이는 자리 | AI가 대체 가능? |
| --- | --- | --- |

| **스프레드시트** | 적 로스터, 아이템 총량, 골드, 강도 점수, 프레임 데이터 | **전부 가능** |
| **에디터 안** | 최종 진실. 메트릭 눈금, 점프 궤적 미리보기, 히트박스 기즈모 | **불가** |

## 5. 짝 문서와 어긋나는 부분 — 곡선 그래프

`2026-08-20-게임기획서구성조사.md` 는 **곡선 그래프를 "직접 만들 1순위"** 로 뒀다. 이 조사는 **"만들지 말 것"** 이라고 한다.

| | 기획서 조사 | 횡스크롤 조사 |
| --- | --- | --- |
| 근거 | 일반 GDD 관행. "숫자만 보면 밸런스 틀어진 걸 못 본다" | 실무자 증언. **"전용 소프트웨어 없다"**, Valve·Journey 모두 표·스프레드시트 |
| 결론 | 곡선 그래프 필요 | **표로 충분** |

**판단** : 횡스크롤 조사 쪽이 **실제 개발자 증언에 근거**하므로 더 무겁다. 곡선 그래프는 **우선순위를 내리고**, 대신 **표 형식(구간 × 강도점수 × 종류)** 을 먼저 지원한다.

다만 기획서 조사의 지적("겹쳐 봐야 밸런스가 보인다")도 틀리지 않으므로, **나중에 실제로 아쉬워지면 그때 만든다.**
