# 설명용 그림 툴 조사

조사일 : 2026-08-19
대상 : `Docs/Todo/AI게임스튜디오.md` 의 "AI의 설명용 그림 툴"
목적 : 기획·설계 문서에 들어갈 그림(UI 화면, 코드 플로우, 시스템 구조도)을 AI가 텍스트만으로 만들게 하기

---

## 결론

### 1. 그림은 두 갈래로 나눈다

| 그리려는 것 | 쓸 것 | 이유 |
| --- | --- | --- |
| 코드 플로우, 시스템 구조도, 순서도, 상태도 | **Mermaid** | AI가 제일 잘 쓰고, 아무것도 안 깔아도 렌더링된다 |
| UI 화면 배치 (와이어프레임) | **직접 만든 와이어프레임 CSS + HTML** | Mermaid로는 UI를 못 그린다 |

하나로 통일하고 싶지만 **Mermaid는 UI 화면을 못 그린다.** 이건 문법 문제가 아니라 기능이 없는 것이라 우회가 안 된다. 그래서 딱 두 갈래로만 나눈다.

### 2. 아스키 아트로 그리는 방식은 버린다

원래 구상(`아스키 이미지 기반 → 나중에 HTML/CSS`)의 **1단계는 하면 안 된다.** LLM이 아스키 아트를 직접 그리는 건 프롬프트로 고칠 수 있는 문제가 아니다. 근거는 아래 3장에.

대신 이렇게 간다.

```
AI → Mermaid 텍스트 → 렌더러가 계산 → 그림
   (무엇을 그릴지)      (자리 맞추기·선 잇기)
```

AI는 "무엇을 그릴지"만 쓰고, **박스 크기·자리 맞추기·선 잇기는 도구가 계산한다.** 이건 프로젝트 원칙인 "AI는 무엇을 만들지만 정하고, 실제로 만드는 일은 툴이 맡는다"와 같은 방향이다.

### 3. 지금 당장 새로 깔 게 없다

Mermaid는 **렌더러를 설치할 필요가 없다.** GitHub·VS Code·Claude Artifact가 알아서 그려준다. 와이어프레임 CSS는 우리가 만드는 파일 한 장이다. 즉 **1단계는 설치 0개로 시작할 수 있다.**

## 1. Mermaid — 기본 그림 도구

### 왜 1순위인가

1. **AI가 제일 잘 쓴다.** 학습 데이터가 압도적으로 많다. LLM 대상 벤치마크(MermaidSeqBench)가 나온 유일한 다이어그램 문법이다.
2. **설치가 0이다.** 아래 표 참고.
3. MIT 라이선스, 별 89k, 조사 당일에도 커밋이 있었다. 유지보수 위험이 가장 낮다.
4. **되돌려 고치기 쉽다.** 텍스트라서 git diff 가 읽히고, AI가 일부만 고칠 수 있다.

### 어디서 그냥 렌더링되는가

| 위치 | 되는가 | 비고 |
| --- | --- | --- |
| **GitHub 웹** | O | `Docs/` 문서에 넣으면 웹에서 바로 그림으로 보인다 |
| **VS Code** | O | **1.121 이상**부터 내장. 그 아래는 확장 설치 필요 |
| **Claude Artifact** | O | ` ```mermaid ` 펜스를 바로 그린다 |
| **Claude Code 터미널** | X | 텍스트 코드블록 그대로 보인다 |

### 안전하게 쓸 수 있는 종류

`flowchart`, `sequenceDiagram`, `classDiagram`, `stateDiagram-v2`, `erDiagram`, `gantt`, `pie`, `mindmap`, `timeline`

**`-beta` 가 붙은 종류는 문서에 쓰지 않는다.** (`architecture-beta`, `block-beta` 등) GitHub이 쓰는 Mermaid 버전이 최신보다 뒤처져 있어서 안 그려질 수 있다.

### 한계

- 노드가 **20~30개를 넘으면** 자동 배치가 지저분해진다
- 배치를 손으로 조정하는 기능이 거의 없다
- 라벨에 괄호나 따옴표를 넣으면 파서가 자주 깨진다 → **라벨은 따옴표로 감싸는 습관**을 들인다
- C4 다이어그램, 배포 다이어그램 없음
- UI 와이어프레임 없음

## 2. UI 와이어프레임 — 후보 두 개가 갈렸다

조사에서 **서로 다른 답**이 나왔다. 둘 다 적어두고 판단 근거를 남긴다.

| | A. PlantUML Salt | B. 직접 만든 와이어프레임 CSS |
| --- | --- | --- |
| 방식 | 텍스트 DSL (`[OK]`, `()`, `"입력칸"`) | AI가 HTML을 쓰고 CSS가 모양을 잡음 |
| 설치 | **Java 필요** (지금 이 PC에 없음) | **없음** (CSS 파일 한 장) |
| 라이선스 | 배포판마다 다름 (GPL/LGPL/MIT…) | 우리 것 |
| 문서에서 바로 보이나 | X (SVG로 뽑아서 이미지로 링크) | X (별도 `.html` 또는 Artifact) |
| AI가 쓰기 | 중간 — 표 문법(`\|`)에서 실수가 잦다 | **쉬움** — HTML/CSS는 LLM이 가장 잘 쓰는 언어 |
| 결과물 | 회색 상자 도면 | 원하는 대로 |

### 판단: B (직접 만든 CSS) 를 1순위로 본다

- Salt는 **Java를 새로 깔아야 한다.** 규칙상 사용자 승인이 필요한 일이고, 얻는 것에 비해 값이 비싸다.
- Salt의 표 문법(`|` 로 칸 나누기)은 **아스키 아트와 같은 종류의 실수**를 부른다. 칸 맞추기를 AI가 해야 한다.
- HTML/CSS는 **LLM이 가장 많이 학습한 언어**다. flexbox/grid가 배치를 계산해 주므로 AI가 좌표를 셀 필요가 없다.
- 외부 의존이 0개라 **Claude Artifact의 CSP 제약**(외부 CDN 차단)을 자동으로 만족한다.

### 만들 것

버튼·입력창·리스트·모달 같은 조각을 클래스 몇 개로 정의한 CSS 한 장.

```
.wf-screen  .wf-btn  .wf-input  .wf-list  .wf-modal  .wf-nav ...
```

AI는 이 클래스를 조합해서 HTML만 쓴다.

### 참고할 것

- **wired-elements** (MIT, 별 10.8k) — 손그림 느낌 UI 컴포넌트. 코드나 아이디어를 가져다 쓰기 좋다. 다만 웹컴포넌트라 JS가 필요해서 그대로 쓰지는 않는다.
- **agilek/wireframer-skill** — 이미 wired-elements + Claude Code 조합으로 만들어진 오픈소스 스킬. 방식이 되는지 확인용 참고 사례.

### 탈락

- **tldraw** — 2025년 9월 라이선스 개편으로 상업 사용 시 유료, 무료는 워터마크. 리스크를 안고 갈 이유가 없다.
- **Excalidraw** (MIT) — 자유형 스케치용이라 UI 배치에는 손이 더 간다. 브라우저 없이 이미지를 뽑을 수 있는지도 정보가 서로 어긋나 확인 못 함.
- **rough.js / roughViz** — 도형·차트 primitive 라서 UI 부품이 없다. 손그림 질감만 얹는 장식용으로는 가능.

## 3. 아스키 아트를 버리는 이유 (중요)

### 근거 1 — 프론티어 모델도 절반은 틀린다

"설명 → 아스키 그림" 생성 정확도.

| 모델 | 정확도 |
| --- | --- |
| GPT-4.1 | 53.6% |
| Qwen3-235B | 46.0% |
| GPT-oss-20B | 44.0% |
| Llama-3-70B | 43.9% |
| Qwen2.5-7B | 16.1% |

**읽기와 쓰기가 비대칭이다.** 같은 모델이 아스키를 *읽는* 정확도는 *쓰는* 정확도보다 13~27%p 높다. 읽기는 패턴 인식이지만, 쓰기는 "모든 요소의 위치가 동시에 맞아야 하는" 전역 제약 문제라서 순차 토큰 예측기가 못 푼다.

### 근거 2 — Claude Code에 실제로 올라온 버그

`anthropics/claude-code` 이슈 #16473:
- 세로선 `│` 이 줄마다 어긋난다
- 고치라고 하면 칸을 직접 세는 대신 **Python 스크립트를 짜서** 문자 위치를 검증하려 든다. 10번 넘게 반복하고도 실패
- 이슈는 **"not planned" 로 닫혔다** — 도구 쪽에서 고칠 계획이 없다

### 근거 3 — 한글이 섞이면 더 심각하다

유니코드 East Asian Width 기준으로 **한글은 고정폭 폰트에서도 2칸을 먹는다.** 그래서 글자 수가 같아도 화면 폭이 다르다. 게다가 폰트마다 전각을 정확히 2칸으로 안 그리는 경우가 있어 **환경마다 다르게 깨진다.**

우리 문서는 한국어다. 아스키 박스에 한글 라벨을 넣고 AI가 폭을 맞추는 건 사실상 불가능하다.

### 흔한 실패 패턴

1. 박스 오른쪽 모서리가 줄마다 다른 칸에 찍힘
2. 세로선이 위아래 줄에서 다른 열로 밀림
3. 라벨이 박스 밖으로 넘침
4. 화살표가 목적지에 안 닿고 끊김
5. 요소 5개 이상이면 전체 배치가 무너짐
6. 한글이 섞이면 전부 어긋남

### 함께 탈락하는 것

**아스키 → SVG 변환기(svgbob, ditaa, aasvg, goat)도 주력으로 못 쓴다.** 이건 그림을 그려주는 게 아니라 *이미 잘 그려진 아스키*를 예쁘게 만드는 도구다. 입력 아스키를 AI가 만들어야 하므로 위 문제가 그대로 남는다. 오히려 더 나쁘다 — 아스키가 살짝 어긋나면 SVG는 선이 아예 끊긴 채로 나온다.

**GUI 에디터도 전부 탈락** — asciiflow, Monodraw, textik 등은 사람이 마우스로 그려야 해서 파이프라인에 못 넣는다.

## 4. 아스키 출력이 정말 필요하다면

터미널에서 봐야 하는 경우에만. **AI가 그리는 게 아니라 도구가 뽑는다.**

| 도구 | 라이선스 | 필요한 것 | 비고 |
| --- | --- | --- | --- |
| **beautiful-mermaid** | MIT | Node만 (`npm i beautiful-mermaid`) | Mermaid → 아스키 + SVG. 헤드리스 브라우저 불필요 |
| **D2** | MPL-2.0 | 단일 실행파일 (`winget install Terrastruct.D2`) | 아스키 렌더러는 **알파** 단계 |
| **mermaid-ascii** | MIT | Go 바이너리 (툴체인 불필요) | flowchart / sequence / ER 만 |

### 아스키를 쓸 때 주의점

- **반드시 코드 펜스 안에 넣는다.** 밖에 두면 Markdown이 공백을 접고 `-`, `|` 를 문법으로 해석한다
- **순수 ASCII(`+-|`) 가 유니코드 박스문자(`┌─┐`)보다 안전하다.** 폰트에 글리프가 없으면 OS가 다른 폰트로 대체하는데, 자간이 달라서 격자가 통째로 무너진다
- 줄 끝 공백을 지우는 에디터 설정이 박스 오른쪽 벽을 먹을 수 있다

## 7. 확인 못 한 것

- **아무 도구도 실제로 설치·실행해 보지 않았다.** 위 내용은 전부 문서와 검색 기준이다.
- `beautiful-mermaid` 의 **아스키 출력 품질**은 실물로 봐야 판단이 확정된다.
- **GitHub이 지금 쓰는 정확한 Mermaid 버전** — GitHub이 공개하지 않는다. 커뮤니티 보고로 v11.4.1(2025-04)이 마지막 단서. `-beta` 타입 회피 권고는 이 불확실성 때문이다.
- VS Code 내장 Mermaid의 지원 타입 목록 — 릴리스 노트에 없음.
- Mermaid / PlantUML / D2 사이의 **LLM 오류율 정량 비교** — 그런 연구를 못 찾았다. 순위는 정성적 관찰 기반이다.
- D2 아스키 렌더러가 알파라는 건 공식 서술이고, **실제로 얼마나 깨지는지는 확인 못 했다.**
- `agilek/wireframer-skill` 저장소의 라이선스.

## 8. 다음에 할 일 (설계 단계에서 정할 것)

1. **10분짜리 확인 작업** — Mermaid를 `Docs/` 문서에 넣고 GitHub 웹에서 실제로 그려지는지 본다. 설치가 필요 없으니 바로 된다.
2. 와이어프레임 CSS 한 장을 설계한다. 어떤 조각(클래스)이 필요한지부터 정한다.
3. AI가 그림을 넣을 때 지킬 규칙을 `Docs/Guide/` 에 한 장으로 정리한다. (어떤 그림에 무엇을 쓰는지, `-beta` 금지, 라벨 따옴표 등)
4. 아스키 출력이 정말 필요한지 판단한다. 필요하면 `beautiful-mermaid` 를 확인해 본다. **패키지 추가는 사용자 승인 대상.**
