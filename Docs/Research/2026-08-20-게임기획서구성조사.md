# 게임 기획서 구성과 필요한 그림 조사

조사일 : 2026-08-20
목적 : "설명용 그림 툴"이 **무엇을 그릴 수 있어야 하는지** 요구사항을 뽑는다
전제 : 2D 횡스크롤, 자유 배치 전투, Unity C#, **1인 + AI 규모**

---

## 결론

### 1. "기획서 한 권"은 인디에서 안 쓴다

2020년대 실무 표준은 이 흐름이다.

```
원페이저(1장) → 기능별 문서(feature brief) → 위키/Notion 에 살아있는 문서
```

처음엔 원페이저 하나로 시작하고, 게임이 커지면 주제별로 갈라진다. 1인+AI 규모면 이 형태가 맞다.

### 2. 반복해서 나오는 그림은 6가지뿐이다

순서도·관계도 / 표 / 화면 와이어프레임 / 2D 공간 배치도 / 곡선 그래프 / 시간축.
나머지(컨셉아트, 무드보드)는 그림 도구가 아니라 **아트 영역**이다.

### 3. 도구 우선순위 — 앞선 설계와 순서가 다르다

| 순위 | 그림 유형 | 도구가 필요한가 |
| --- | --- | --- |
| — | **표** | **최다 빈도인데 마크다운으로 끝.** 도구 불필요 |
| 1 | **노드-엣지** (코어 루프, AI 상태도, 화면 전이) | **Mermaid로 충분.** 만들 게 아니라 **잘 쓰는 규칙**을 정한다 |
| **2** | **곡선 그래프** (밸런스·성장·난이도) | **없음 → 직접 만들 1순위** |
| **3** | **시간축** (공격 선딜/판정/후딜) | **없음 → 2순위** |
| **4** | **2D 공간 배치** (레벨, 적 배치, 히트박스) | 없음 → 3순위 |
| **5** | **UI 와이어프레임** | 없음 → 4순위 |

> **`DiagramTool/Docs/Design/2026-08-20-설명용그림툴설계.md` 는 와이어프레임을 1순위로 잡았다. 그건 틀렸다.** 와이어프레임은 "빈도는 높지만 종류가 몇 개 안 된다"(HUD 1개, 메뉴 몇 장)라서 뒤로 밀린다.

### 4. 엔진 2개면 4개를 다 덮는다 — 가장 쓸모 있는 발견

- **곡선 그래프(②) + 시간축(③)** → 자료 구조가 같다. **시간축 위에 값이나 구간을 얹는 것**
- **2D 배치(④) + 와이어프레임(⑤)** → 같다. **2D 평면 위 사각형 배치**

즉 만들 것은 4개가 아니라 **2개**다.

### 5. 액션 게임이라 시간축이 3순위로 올라왔다

일반 기획서에선 드물다. 그런데 **2D 액션은 공격의 선딜/판정/후딜이 게임의 본체**다. 텍스트로 "선딜 짧음"이라고 쓰면 아무 정보도 전달되지 않는다.

## 2. 기획서 구성

### 2-1. 표준 GDD 목차 (템플릿 공통)

**개요 / 메커니즘 / 스토리 / 레벨 / UI / 아트·사운드 / 기술 / 일정** 8개가 사실상 표준이다. 템플릿마다 이름만 다르다.

### 2-2. 실무의 축약형

"GDD가 없어졌다"가 아니라 **쪼개졌다.**

- **원페이저** — 게임 전체를 1장으로. 발표용이 아니라 **읽히는 용도**
  - 항목: 제목·로고 / 장르·플랫폼 / 타겟 / 전제와 세계관 / 비주얼 스타일 / **코어 루프** / 핵심 기능·차별점 / 경쟁작 / 팀·상태 / 수익모델
- **기능 문서(feature brief)** — 기능 하나당 문서 하나. 원페이저 형식
- **위키/Notion 기반 살아있는 문서** — 계속 고친다

### 2-3. 인디·1인 분량

- 인디 GDD는 보통 **10~30쪽**. High Concept 2~3쪽
- 첫 프로토타입이나 게임잼은 **1쪽이면 충분**. 언더테일 토비 폭스는 **2쪽으로 시작**해서 필요할 때만 늘렸다
- 인디는 **지침(guidepost)** 이지 설계도(blueprint)가 아니다
- 인디가 실제로 넣는 시각자료로 꼽힌 건 딱 3가지 — **컨셉아트·무드보드 / 플로우차트 / 플레이어 여정 맵**
- **반대 의견도 있다.** 어떤 가이드는 다이어그램을 하나도 권하지 않고 "간결·정확·정리" 세 원칙만 말한다. 즉 그림은 필수가 아니라 **텍스트로 애매해질 때만** 쓰는 도구다

### 2-4. 한국 업계 관행

표준 목차 (모바일 기준):

```
개요 → 유사 게임 분석 → 세계관 → 구조 및 형태 → Game System → Game Screen → 사운드 리스트
```

국내 관행에서 확실히 드러나는 것:
- **"구조 및 형태"에 Flow Chart와 UI 설계안**이 들어간다
- **"Game Screen"에 게임 화면 시안**이 들어간다
- 즉 **플로우차트 + UI 시안을 사실상 필수**로 본다

「프로그래머에게 사랑받는 게임 기획서 작성법」의 결론은 **"기획서의 형식을 없애자"** 다. 대신 실제로 쓰이는 것:
- **상태도** — 몬스터 AI를 "평화 → 경계 → 공격 → 도주"로
- **데이터 테이블 참조** — 수치를 문장이 아니라 `MeatParam.RegenTime` 같은 **데이터시트 키**로 지정
- **단계 구분** — 확정 사양 / 당장의 사양 / 미래 비전을 나눠서

국내 최소 기획서 가이드는 8항목만 든다: 콘셉트 / 세계관 / 주요 인물 / 진행 구조 / 전투 / 성장 / 콘텐츠 목록 / 제작 범위. 시각자료는 **표·체크리스트·진행 플로우뿐**이고, **그림보다 표가 더 많다.**

## 3. 항목별 상세

### 핵심 루프

**순환 화살표 도식.** 줌아웃 뷰이지 상세 설명용이 아니다. 그리는 법 두 가지:

- **명사/동사 다이어그램** — 중요한 사물 사이에 선을 긋고 행동을 적는다. 예: `Ghosts -Chase-> Player`, `Player -Eats-> Dots`
- **동사 나열 후 연결** — 플레이어가 하는 동사를 적고 무엇이 무엇으로 이어지는지 잇는다

**반드시 닫힌 순환이어야 한다.**

### 레벨 디자인 — 가장 구체적으로 확인된 부분

실무 서적(Level Design Book) 기준 3단계:

1. **버블 다이어그램** — 방 하나를 타원 하나로. 크기·연결만. → **노드-엣지**
2. **탑다운 레이아웃** — 벽·문·주요 지형 평면도. *"크게 시작해라. 페이지 전체를 써라. 큰 덩어리부터."* 선 굵기·음영으로 구역 구분
3. **크리티컬 패스** — 시작/출구, **번호 붙은 주요 비트**, 의도한 이동 경로 화살표

> **화살표가 지형과 정확히 안 맞아도 된다.** 의도 전달이 목적이다.

크리티컬 패스 밖 영역을 보면 "안 만들어도 되는 곳"이 보여서 **범위 줄이기 도구**로도 쓴다.

**책 자체의 경고** : *"도면은 마법이 아니다. 레이아웃 도면만으로는 레벨이 되는지 알 수 없다."* 실제 검증은 블록아웃 + 플레이테스트다.

### 페이싱 차트

**X축 = 시간(분), Y축 = 강도(0~100%).**

- 강도는 난이도가 아니다. *"사랑받는 캐릭터의 죽음은 난이도 0의 컷신이지만 감정 강도는 높다."*
- 표현 3가지 : **비트 종류별 색 막대그래프** / **강도 곡선** / 여러 지표 동시 추적 스프레드시트
- 밸브식 비트 분류 : 탐험(낮음) / 전투(높음) / 연출(중간, 전환) / 퍼즐(간격 벌리기)
- 원칙 : **높낮이를 번갈아** 배치

### 경제 / 자원 — Machinations 표기법

| 요소 | 모양 | 뜻 |
| --- | --- | --- |
| Pool | 빈 원 | 자원 저장소 |
| Source | 위 삼각형 | 자원 생성 |
| Drain | 아래 삼각형 | 자원 소멸 |
| Converter | 오른쪽 삼각형+세로선 | 자원 변환 |
| Gate | 마름모 | 확률/조건 분배 |

**→ 1인 개발에는 과하다.** 소지금·경험치 정도면 표로 충분하다.

### 데이터 구조

국내 관행 : **데이터 테이블 정의서**(엑셀/시트) + 문서에서의 **키 참조**. 문서에 수치를 직접 박지 않는다.
ER 다이어그램 같은 정식 표기까지 쓰는지는 **공개 사례에서 확인 못 했다.**

| 유형 | 예 | 빈도 | 코드로 가능? | Mermaid로 되나? |
| --- | --- | --- | --- | --- |
| **① 노드-엣지** | 코어 루프, AI 상태도, 화면 전이, 스테이지 흐름, 스킬트리, 방-연결 | **매우 높음** (그림의 절반 이상) | 완전 가능 | **잘 됨** |
| **② 표·수치** | 스탯표, 아이템표, 기능 우선순위 | **매우 높음** | 마크다운으로 끝 | 해당 없음 |
| **③ 곡선·그래프** | 난이도 곡선, 성장 곡선, 페이싱 차트, 능력치 비교 | **높음** | 가능 (SVG) | **사실상 안 됨** |
| **④ 화면 배치** | HUD, 메뉴, 인벤토리 | **높음** | 가능 (박스 쌓기) | **안 됨** |
| **⑤ 2D 공간 배치** | 레벨 탑다운/횡단면, 적 배치, 크리티컬 패스, 히트박스 | **높음** | 개념도는 가능, 실제 지형 스케치는 어려움 | **안 됨** |
| **⑥ 시간축** | 공격 프레임, 컷신 비트, 간트 | **중간** (액션은 높음) | 가능 (막대 배치) | gantt로 억지 |
| **⑦ 이미지·아트** | 컨셉아트, 무드보드, 일러스트 | **높음** | **불가** | 불가 |

## 5. 1인+AI 에서 진짜 필요한 것

### 남길 것 (5개)

1. **노드-엣지** — 코어 루프, AI 상태도, 화면 전이, 스테이지 흐름. 하나로 다 커버
2. **곡선 그래프** — 1인 개발에서 밸런스가 제일 자주 틀어지는데, **숫자만 보면 틀어진 걸 못 본다**
3. **공격 프레임 타임라인** — 2D 액션이라서
4. **2D 공간 배치도** — 자유 배치 전투라 "어디에 몇 마리를 얼마 간격으로"가 곧 기획
5. **UI 와이어프레임** — 자주 그리진 않지만 안 그리면 매번 말로 설명해야 한다

### 뺄 것

| 뺄 것 | 이유 |
| --- | --- |
| 시장 분석, 페르소나, 경쟁작 포지셔닝 | **투자자용.** 1인 개발엔 무의미 |
| 간트 차트 | 팀 일정 조율용. 혼자면 할 일 목록이면 된다 |
| Machinations식 정식 경제 다이어그램 | 그럴 경제가 없다 |
| 시스템 아키텍처도 | **코드를 보면 된다.** 문서로 유지하면 금방 거짓말이 된다 |
| 무드보드 도구 | 이미지 붙이기지 그리기가 아니다 |

## 6. 코드로 그릴 수 있는 것 / 없는 것

| 코드로 완전히 가능 | 경계선 | 사람·이미지가 해야 함 |
| --- | --- | --- |
| 관계도·순서도·상태도 | **레벨 레이아웃** — 개념도는 코드, 지형의 실제 느낌은 손그림 | 컨셉아트 |
| 표 | **캐릭터 비율** — 상자 비교는 코드, 실루엣은 그림 | 무드보드 |
| 곡선·그래프 | **UI 시안** — 배치는 코드, 최종 룩은 아트 | 캐릭터 일러스트 |
| 타임라인·프레임 차트 | | 아트 스타일 정의 |
| 와이어프레임 | | |
| 히트박스 사각형 배치 | | |

### 경계 기준 한 줄

> **"위치와 관계와 수치만 있으면 뜻이 통하는가?"** 통하면 코드. 질감·분위기·감정이 필요하면 사람.

기획서 그림의 대부분은 앞쪽이다.

---

## 7. 곡선 그래프를 어떻게 만들 것인가

**Mermaid로 하지 마라.** `xychart-beta` 가 있지만 축 제어·다중 시리즈·로그축·눈금 라벨이 다 부족하고, `-beta` 라 GitHub에서 안 그려질 수 있다.

### 권장 형태

1. **데이터는 표로 먼저 쓴다** (마크다운 표 또는 CSV). 사람과 AI 둘 다 읽고 고칠 수 있어야 한다
2. **그림은 그 표에서 SVG로 생성한다.** 필요한 최소 기능:
   - X/Y축 + 눈금 + 라벨
   - **다중 시리즈 겹쳐 그리기** — 플레이어 공격력 vs 적 체력. **겹쳐야 밸런스가 보인다**
   - 선형/로그 축 전환
   - 계단형(레벨별 이산값)과 곡선(연속) 둘 다
   - **구간 색칠** — 페이싱 차트의 탐험/전투/퍼즐 구분
   - 기준선·목표선 — 예: "여기 넘으면 원킬"
3. **페이싱 차트는 곡선이 아니라 색칠한 막대열**이 원형에 가깝다. 같은 엔진으로 만들 수 있다

### 핵심

> **표 ↔ 그림 왕복.** AI가 표를 고치면 그림이 따라 바뀌어야 한다.

그림을 직접 편집하는 도구는 1인+AI 방식에 안 맞다.

---

## 8. 프레임 데이터 표현

**2D 액션이면 반드시 필요하다.**

확인된 것 — 액션/대전 게임의 공격은 **프레임 단위 3구간**으로 문서화된다.

| 구간 | 뜻 |
| --- | --- |
| **Startup (선딜)** | 입력부터 효과 발생까지 |
| **Active (판정)** | **히트박스가 존재하는 프레임 구간** |
| **Ending (후딜)** | 효과 종료부터 다음 입력 가능까지 |
| Autocancel 등 특수 구간 | 특정 타이밍에만 다른 동작으로 전환 |

기준 : 60fps에서 1프레임 = 약 16.7ms

### 필요한 그림 형태

**여러 개의 라벨 붙은 가로 막대를 같은 시간축 위에 쌓는 것.** 간트 차트와 자료 구조가 완전히 같다.

```
공격: 강베기 (총 34F)
  선딜     ████████░░░░░░░░░░░░░░░░░░░░░░░░░░  1-8F
  판정     ░░░░░░░░████░░░░░░░░░░░░░░░░░░░░░░  9-12F   히트박스 A
  후딜     ░░░░░░░░░░░░██████████████████████  13-34F
  캔슬가능 ░░░░░░░░░░░░░░░░░░░░████████░░░░░░  21-28F
  무적     ██████░░░░░░░░░░░░░░░░░░░░░░░░░░░░  1-6F
```

여기에 **히트박스 배치도**(캐릭터 기준 사각형 위치)를 붙이면 공격 하나가 완전히 기술된다.
같은 도구가 **컷신 비트, 보스 패턴 사이클, 콤보 타이밍**에도 그대로 쓰인다.

> **주의 : 위 막대 형식은 업계 표준 서식이 아니다.** 확인된 개념(선딜/판정/후딜/무적/캔슬)에서 조사자가 구성한 것이다. 공개 기획서에 이런 그림이 실제로 들어있는지는 **확인 못 했다.**

---

## 9. 확인 못 한 것

- **2D 횡스크롤 실사례 기획서를 직접 열어보지 못했다.** Diablo 피치 문서, Rogue Legacy 디자인 노트, Pid GDD, Captain Claw GDD 는 스캔 PDF이거나 접근이 막혀 있었다. **이번 조사의 가장 큰 구멍**
- **공개 GDD 안의 프레임 데이터 표기 실물** — 개념·구간 정의는 확인했으나 "기획자가 어떤 그림으로 그리는가"의 실제 사례는 못 찾았다
- KOCCA 「게임 기획서 표준양식 개선안 연구」 PDF — 내려받았으나 본문 추출 실패
- Unity 공식 GDD 템플릿 PDF 본문 — 추출 실패. 목차는 2차 자료로만 확인
- 데이터 구조에 ER 다이어그램 같은 정식 표기를 쓰는지
- **세션 웹 검색 예산(200회)이 소진되어** 마지막엔 URL 직접 열기로만 진행했다. 추가 한국어 자료(특히 시스템 기획서 실무 사례)를 넓게 훑지 못했다
