## 1. 핵심 발견 — 타일맵은 아스키 아트가 아니다

앞선 조사에서 **"LLM은 아스키 아트를 못 그린다"** 는 결론이 났다. 그런데 **타일맵은 다르다.**

| | 아스키 박스 그림 | 타일맵 |
| --- | --- | --- |
| 무엇인가 | **그림** | **2차원 배열** |
| AI가 하는 일 | 박스 크기 맞추기, 선 잇기, 라벨 넣기 | **한 줄씩 문자 찍기** |
| 1칸 틀리면 | **그림이 깨진다** | **타일 하나가 틀린다** (국소적) |
| 검증 | 사람이 눈으로 봐야 함 | **모든 줄 길이가 같은지 기계가 검사** |

즉 타일맵은 **그림이 아니라 데이터**다. 그래서 AI가 써도 안전하다.

> **3D였다면 불가능했을 것이 2D 타일 기반이라 가능하다.** 이게 이 프로젝트의 핵심 기회다.

단, **행 길이 검증기가 반드시 있어야 한다.** 이게 없으면 아스키 아트와 같은 문제가 된다.

## 2. 만들 것

### 엔진 3개로 필요한 그림 대부분을 덮는다

| 엔진 | 무엇 | 덮는 그림 |
| --- | --- | --- |
| **A. 격자·평면** | 2D 평면 위 칸/사각형 배치 | 레벨 타일맵, 방 템플릿, 퍼즐 판, 적 배치, UI 와이어프레임 |
| **B. 시간축** | 시간축 위 구간 막대 | 공격 프레임 타임라인, 구간·층 페이싱, 보스 페이즈, **분포 막대** |
| **C. 관계 표 린터** | **표 → 검사 보고서 + Mermaid** | 생산 사슬, 테크 트리, 카드 표, 시너지·아키타입, 언락 순서 |

**C 는 그림 도구가 아니라 검사 도구다.** 그림은 Mermaid 가 그린다. 우리는 표를 훑어 **구멍을 잡는다.**

### 도면 프로필 — 장르 차이는 여기로 흡수한다

**툴을 장르별로 쪼개지 않는다.** 그림 툴에서 정한 "툴 하나 + 프로필 설정 파일"과 같은 구조다.
장르가 섞이는 게임(농장 경영 + 던전 탐험, 로그라이트 + 덱빌딩)이 흔해서, 쪼개면 오히려 못 다룬다.

프로필이 정하는 것은 **딱 두 가지**다.

| 프로필이 고르는 것 | 예 |
| --- | --- |
| **범례** — 어떤 문자를 쓰나 | 던전 = `+`문 `K`열쇠 / 소코반 = `$`상자 `*`목표 / 방 템플릿 = 출입구 4방향 |
| **켤 검사 목록** — 무엇을 오류로 볼 것인가 | 테크 트리는 순환을 오류로, **생산 사슬은 순환을 정상으로** |

> ⚠️ **검사 목록을 고정하면 안 되는 이유** — 7장 "순환" 항목 참고.
> 광산이 곡괭이를 쓰고 → 철광석을 내고 → 대장간이 곡괭이를 만드는 순환은 **일부러 넣는 것**이다.

### 만들 순서

| 순서 | 만들 것 | 크기 | 왜 이 순서인가 |
| --- | --- | --- | --- |
| **0** | `../Guide/그림그리기.md` — **Mermaid 사용 규칙** | 작음 | 만들 게 아니라 **정할 것**. 가장 자주 쓰는데 도구가 이미 있다 |

## 3. 엔진 A — 격자·평면

### 3-0. 격자의 뜻은 **이동 축**이 정한다

축 3개 중 **도면을 바꾸는 건 이동 축 하나뿐**이다.

| 축 | 도면에 미치는 영향 | 무엇이 바뀌나 |
| --- | --- | --- |
| **이동** (평면 / 중력+점프) | **크다** | 격자의 뜻, 범례 기호, 검증기 4번, 기준선 표 |
| **투영** (정면/탑다운/쿼터뷰/아이소) | 작다 | **렌더러만.** 문자 격자는 그대로 |
| **방향 수** (1/4/8) | 없다 | 스프라이트 장수 문제라 도면과 무관 |

**투영이 격자를 안 건드리는 이유** : 아이소메트릭도 속은 정사각 격자고 그리는 법만 마름모다.
(`Todo/그림툴.md` — "47-blob 은 위상이 정사각과 같다") 그래서 **표기법은 하나, 렌더러만 갈아끼운다.**

| 이동 축 | 격자가 뜻하는 것 | 가로 · 세로 |
| --- | --- | --- |
| **중력+점프** | 옆에서 본 **단면** | 가로=거리, 세로=**높이** |
| **평면** | 위에서 본 **평면도** | 가로세로 **둘 다 바닥** |

---

### 3-1. 레벨 타일맵 (1순위)

**입력** : 문자 그리드 + 범례. 그리드 머리에 **이동 축을 적는다.**

#### 중력+점프 (단면)

````markdown
```tilemap name="1-1 첫 구간" tile=16 move=gravity 예시=참
.....................................
..........C..........................
.......####..........E...............
.....................####............
..P..................................
#####....######......................
#####....######...............#######
    ^^^^^^      ^^^^^^^^^^^^^^^
```
범례: P=시작 #=지형 C=수집물 E=적 ^=낭떠러지 S=체크포인트
````

#### 평면 (평면도)

````markdown
```tilemap name="던전 1층" tile=16 move=flat 예시=참
#########################
#....C..#........#......#
#.......+........#..E...#
#..P....#....E...+......#
#.......#........#...K..#
####+####........#......#
#.......#############...#
#...E...........K.......#
#########################
```
범례: P=시작 #=벽 .=바닥 +=문 K=열쇠 E=적 C=수집물 X=출구
````

#### 방언 — 장르별로 격자를 조금씩 늘린다

**정본은 언제나 ASCII 한 글자다.** 아래는 기존 표기법에 얹는 것이지 바꾸는 게 아니다.

**① 방 템플릿 (`roomtemplate`) — 로그라이크**

절차 생성 게임은 레벨 한 장을 안 그린다. **부품(방)** 과 **조립 설명서(층 그래프)** 를 따로 그린다.
Enter the Gungeon 은 스테이지당 방을 **약 300개** 손으로 그리고 각각 따로 플레이테스트했다.

````markdown
```roomtemplate id=prison_LR_01 size=10x8 move=gravity biome=prison 예시=참
##########
>........<
>..#..#..<
>........<
>...EE...<
>..####..<
>........<
##########
```
범례: #=지형 .=빈칸 E=적 >=서쪽 출입구 <=동쪽 출입구 ^=위 출입구 v=아래 출입구
````

기존 문자는 **하나도 안 바꾼다.** 출입구 4개와 머리말 `size` · `biome` 만 는다.

**② 소코반 (`puzzle=sokoban`) — 퍼즐**

업계 표준 텍스트 포맷(**XSB**, `.sok`)이 이미 우리 표기법과 문법이 같다. 벽이 `#` 인 것까지 같다.
**그래서 XSB 를 그대로 받아들인다.** (관용 표기라 라이선스 문제 없음)

````markdown
```tilemap name="창고 1" tile=16 move=flat puzzle=sokoban 예시=참
#######
#.....#
#.$.*.#
#..@..#
#######
```
범례: #=벽 .=목표 $=상자 *=목표 위 상자 @=플레이어 +=목표 위 플레이어
해답: lluurDDD
````

**해답은 그림이 아니라 문자열 한 줄이다.** `LURD` 표기 — 대문자는 상자를 밀며 이동, 소문자는 그냥 이동.
렌더링할 게 없고 **검증기 입력으로 바로 들어간다.**

> ⚠️ 소코반에서는 `.` 이 바닥이 아니라 **목표**다. XSB 를 따르기 때문이다.
> **방언마다 범례가 다를 수 있다** — 그래서 범례를 그리드 바로 아래 적는 규칙이 중요하다.

**규칙 (양쪽 공통)**
- 한 칸 = 한 문자 = 한 타일
- **모든 줄의 길이가 같아야 한다** ← 검증기가 검사
- 범례는 그리드 바로 아래. 프로젝트 공통 기호를 `Guide/타일기호.md` 에 정해둔다
- 한 화면은 대략 **40×23 타일**. 그보다 크면 구간을 나눈다

**범례 기호는 공통 / 이동별로 나눈다**

| 구분 | 기호 |
| --- | --- |
| 공통 | `P` 시작 `#` 막힘 `.` 빈칸 `E` 적 `C` 수집물 `S` 체크포인트 |
| 중력+점프 전용 | `^` 낭떠러지 `~` 사다리·밧줄 |
| 평면 전용 | `+` 문 `K` 열쇠 `X` 출구 |

**왜 이 형태인가**
- 실제 개발사(Yacht Club)가 **"오브젝트 목록 + 구간별 거친 그림"** 으로 시작한다
- *Super Mario Bros.* 분석 — **"모든 발판은 지면에서 4블록 또는 8블록 위"**. **블록 개수가 설계 언어**다
- 적 배치·체크포인트·수집물은 **별도 도면이 아니라 이 위의 주석**이다. 그래서 한 장에 다 담는다

**검증기가 할 일**

1~3번은 양쪽 공통, **4번이 이동 축에 따라 갈린다.**

| # | 검사 | 이동 축 |
| --- | --- | --- |
| 1 | 모든 줄 길이가 같은가 | 공통 |
| 2 | 범례에 없는 문자가 있는가 | 공통 |
| 3 | 시작점(`P`)이 정확히 1개인가 | 공통 |
| 4a | **점프로 못 올라가는 발판이 있는가** (점프 아크) | 중력+점프 |
| 4b | **걸어서 못 가는 칸이 있는가** (이어짐 검사) | 평면 |
| 5 | **방 안에서 모든 출입구가 서로 이어지는가** | 방 템플릿 |
| 6 | 출입구가 규격 위치에 있는가 (서쪽=0열, 동쪽=마지막 열…) | 방 템플릿 |
| 7 | 방 크기가 `size` 와 같은가 | 방 템플릿 |
| 8 | **출입구 조합별로 방이 최소 1개씩 있는가** (좌우 / 좌우아래 …) | 방 템플릿 |
| 9 | **퍼즐이 풀리는가 · 최소 몇 수인가 · 우회 해답이 있는가** | 소코반 |

> **4번이 이 도구의 존재 이유다.** 그림을 예쁘게 그리는 게 아니라 **기계가 "여기 못 간다"를 잡아주는 것.**
> 재는 방법만 다르고 값어치는 같다.

**4b 이어짐 검사** : 시작점 `P` 에서 사방으로 번져 나가(flood fill) 닿는 칸을 표시한다. 안 닿는 바닥이 있으면 잡는다.
문 `+` 과 열쇠 `K` 를 같이 넣으면 **잠금-열쇠 순서가 꼬였는지**까지 잡힌다 — 열쇠가 그 문 뒤에 있으면 영영 못 연다.

**5번은 4a/4b 를 방 하나에 그대로 돌리는 것이다.** 새로 짤 게 없다. 들어왔는데 못 나가는 방을 잡는다.
**8번은 표 한 번 세면 끝인데** 생성기가 막다른 곳에서 멈추는 것을 막는다. 둘 다 값에 비해 아주 싸다.

> **절차 생성의 치명적 실수는 "만들어진 던전을 못 깬다"이다.** 가상의 문제가 아니다 —
> Spelunky 2 도 *"생성기가 보통 입구→출구를 뚫지만 방 안 블록이 무작위라 드물게 출구를 막는다"* 고 기록돼 있고,
> Unexplored 는 아예 게임 안에 **"Pray For Help"** 를 넣어 진행을 막는 게 뭔지 게임이 판정해 고쳐준다.

**9번 퍼즐 솔버** : BFS/A* + 데드락 가지치기로 실제로 풀어본다. 답할 수 있는 것이 셋이다 —
① 풀리는가 ② 최소 몇 수인가 ③ **의도한 답 말고 쉬운 우회로가 있는가**(솔버 최적해와 적어둔 해답을 비교).

> **다른 장르는 "막힌 데 있나"만 보지만 퍼즐은 "이 판이 제대로 된 판인가"까지 기계가 답한다.**
> 소코반은 PSPACE-complete 라 최악의 경우 지수적이지만, 사람이 만든 실전 판(40×23 이내)은 초 단위에 풀린다.
> **정량 벤치마크가 아니라 정황 근거다. 솔버에 시간 제한을 반드시 넣는다.**
> 솔버 코드는 가져오지 않는다 — 쓸 만한 구현이 GPL 이거나 라이선스가 불분명하다. **알고리즘만 보고 직접 짠다.**

**렌더러**
문자 그리드 → 색칠된 HTML 격자. 타일 종류마다 색을 준다. 브라우저나 Artifact로 본다.
**투영 축은 여기서만 쓴다** — 정사각으로 그릴지(정면·탑다운·쿼터뷰) 마름모로 그릴지(아이소). **아이소 마름모는 뒤로 미룬다.**

#### 표기 문자 — 정본은 ASCII, 눈에 편한 건 렌더러가 한다

`#` 과 `.` 만 있는 격자가 읽기 힘든 건 사실이다. 그래도 **정본은 ASCII 로 둔다.**

| 겹 | 무엇 | 문자 |
| --- | --- | --- |
| **정본** | 저장 · AI 출력 · 검증기 입력 · git | ASCII 한 글자 |
| **보기** | 사람이 읽는 것 | 렌더러가 바꿔 찍는다 |

정본을 ASCII 로 두는 이유 :

- **이 툴의 목적이 토큰 절약이다.** AI 가 찍기 쉽고 싼 게 1순위다
- **정렬이 안 깨진다.** `■` `□` `█` 같은 네모 기호는 유니코드 **"모호폭(Ambiguous)"** 이라
  **폰트에 따라 1칸이 되기도 2칸이 되기도** 한다. `■` 와 `.` 를 섞으면 한글 폰트에서 줄마다 길이가 어긋나 보인다.
  **문자 수는 맞는데 눈에는 틀어져 보이는** 제일 나쁜 상태다
- XSB 표준과 호환되고, IME 없이 키보드로 바로 친다

**사람을 위한 것은 HTML 렌더러다.** 그게 원래 설계 의도다. 그 밖에 이만큼만 더한다 :

- `Guide/타일기호.md` 에 **보기 기호 매핑표** (`#` → `█`, `.` → `·`)
- 렌더러에 **마크다운용 미리보기 출력** — HTML 을 못 여는 자리(터미널)에서 쓴다
- **검증기는 정본만 검사한다.** 보기 겹은 검사 대상이 아니다

> 바닥을 빈칸으로 두면 더 읽히지만, 편집기가 줄 끝 공백을 지운다. **`.` 을 그대로 쓴다.**

### 3-2. 이동 기준선 표 (2순위 — 표라서 서식만 정하면 끝)

**이동 축에 따라 서식이 둘이다.** 평면에는 점프 파라미터가 아예 없다.

#### 중력+점프

| 항목 | 값 (타일) | 비고 |
| --- | --- | --- |
| 점프 최고 높이 | 4 | `h` |
| 점프 최대 거리 | 5 | 달리기 상태 |
| 정점까지 거리 | 2.5 | `x_h` |
| 수평 속도 | 8 타일/초 | `v_x` |
| 낙하 최대 안전 높이 | 6 | |

**점프 아크 곡선은 그리지 않는다.** GDC 발표가 증명하듯 곡선은 **파라미터를 뽑기 위한 중간 과정**이고, `h` · `x_h` · `v_x` 세 값이면 곡선이 완전히 결정된다.

> **2026-08-21 고침 — 검사 4a 가 `x_h` 를 실제로 읽는다.**
> 처음 구현은 높이 예산과 가로 예산을 **따로** 썼다. 그러면 *"최고 높이까지 올라간 채로 최대 거리만큼 옆으로 간다"* 가 되는데 실제로는 그럴 수 없다.
> **그래서 견본 도면 하나가 실제로 못 깨는 도면인데 "문제 없음" 이 나왔다.**
>
> | 가로로 간 칸 수 | 올라가 있을 수 있는 최고 높이 |
> | --- | --- |
> | `x_h` 이하 | `h` — 달리는 속도를 줄이면 정점이 앞으로 온다 |
> | `x_h` 초과 | `h × (1 − ((m − x_h) / x_h)²)` |
>
> **곡선을 그리지는 않지만 곡선으로 재기는 한다.** 세 값이면 곡선이 결정된다는 말이 바로 그 뜻이다.

#### 평면

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 이동 속도 | 5 타일/초 | |
| 대시 거리 | 3 타일 | 없으면 비운다 |
| 대시 쿨타임 | 0.8 초 | |
| 몸 크기 | 1 타일 | **통로 최소 폭을 정한다** |
| 시야 반경 | 8 타일 | 적이 나를 알아채는 거리 |
| 상호작용 거리 | 1.5 타일 | 문·상자 여는 거리 |

**몸 크기가 여기서 제일 중요하다.** 이게 있어야 검증기 4b 가 *"이 통로는 좁아서 못 지나간다"* 를 잡는다.
중력+점프의 점프 높이와 같은 자리에 있는 값이다.

### 3-3. 히트박스 — 그리지 않는다

**표로만 적는다.**

| 기술 | 사거리 | 히트박스 (가로×세로) | 오프셋 | 지속 |
| --- | --- | --- | --- | --- |
| 약베기 | 1.5타일 | 24×16 px | (+12, 0) | 3F |

## 4. 엔진 B — 시간축

### 4-1. 공격 프레임 타임라인 (3순위)

**입력** : 표

```
기술: 강베기 (총 34F)
| 구간 | 프레임 |
|---|---|
| 선딜 | 1-8 |
| 판정 | 9-12 |
| 후딜 | 13-34 |
| 캔슬가능 | 21-28 |
| 무적 | 1-6 |
```

**출력** : 같은 시간축 위에 쌓인 막대

```
강베기 (34F)
  선딜     ████████··························
  판정     ········████······················
  후딜     ············██████████████████████
  캔슬가능 ····················████████······
  무적     ██████····························
```

**왜 필요한가**
- 프레임 데이터는 **격투게임 전용이 아니다.** 디자이너 글 제목이 *"**모든** 게임 디자이너가 알아야 할 프레임 데이터 패턴"* 이다
- 실제 엔진 작업이 이 형태다 — Unreal의 **Anim Notify State** 가 애니메이션 타임라인 위 **구간**으로 무기 콜리전을 켜고 끈다
- **표로는 관계가 안 보인다.** 여러 기술을 세로로 쌓아야 상호 유불리가 눈에 들어온다

**핵심** : 사람이 막대를 그리지 않는다. **표를 쓰면 도구가 막대를 만든다.**

### 4-2. 구간 페이싱 표

| 구간 | 종류 | 강도(0~5) |
| --- | --- | --- |
| 1 | 탐색 | 1 |
| 2 | 전투 | 4 |
| 3 | 휴식 | 0 |
| 4 | 전투 | 5 |

**곡선이 아니라 표다.** 실무자가 **"전용 소프트웨어는 없다"** 고 못박았고, Valve도 *Journey* 도 스프레드시트를 썼다.

같은 엔진으로 색 막대열을 뽑을 수 있다. **원칙 : 높낮이를 번갈아 배치한다.**

**이 표는 세 군데에 겸용한다.** 서식은 그대로 두고 첫 열 이름만 바꾼다.

| 첫 열 | 쓰임 | 장르 |
| --- | --- | --- |
| 구간 | 레벨 페이싱 | 액션 |
| **층** | 런 진행 곡선 | 로그라이크 |
| **판 번호** | **기믹 도입 순서** (도입 → 변주 → 조합 → 시험) | 퍼즐 |

### 4-3. 개수축 모드 — 시간 대신 개수를 받는다

엔진 B 는 이미 "표 → 막대"를 한다. **가로축이 시간이 아니라 개수인 모드**만 더하면 분포를 그릴 수 있다.
새 엔진이 아니라 **모드 하나**다.

```
비용별 장수 (목표 → 실제)
 0-1  █          1 / 1
 2    █████      5 / 5
 3    ██████     6 / 6
 4    ███        3 / 3
 5              0 / 2   ← 구멍
 6+   █          1 / 1
```

덱빌딩의 "비용 곡선"이 실제로는 **6칸짜리 표**다. 곡선을 그릴 일이 아니라 **어느 칸이 0인지 보는 일**이다.

## 5. 엔진 C — 관계 표 린터

**그림 도구가 아니라 검사 도구다.** 시뮬레이션·타이쿤과 덱빌딩이 따로 요구했는데 뜯어보니 같은 물건이었다.
생산 사슬(건물·자원)이든 카드 표(카드·아키타입)든 **표를 넣으면 검사 보고서가 나오고, 그림은 Mermaid 가 그린다.**

### 5-1. 왜 렌더러를 안 만드나

이 장르 개발자가 설계 첫날 그리는 건 방향 그래프다. 1849 개발자(SomaSim) 증언 :

> *"설계 단계에서 모든 자원 사슬을 커다란 방향 그래프로 그렸다. **각 노드가 건물이고 각 간선이 자원**이다."*

**그런데 그 그림은 Mermaid 로 이미 된다.** 선례도 있다 — Anno 1800 생산 사슬 렌더러가 실제로 Mermaid 로 그린다(ISC).
그래서 우리가 만들 건 **표를 훑어 구멍을 잡는 쪽**이다.

### 5-2. 입력 — 표다. 그림이 아니다

기존 원칙 그대로 **AI 는 표만 뱉고 코드가 Mermaid 를 만든다.**

**생산 사슬**

````markdown
```chain profile="tycoon" 예시=참
| 건물 | 넣는 것 | 나오는 것 | 초당 | 해금 테크 |
|---|---|---|---|---|
| 밀농장 | — | 밀 2 | 1 | — |
| 빵집 | 밀 2 | 빵 1 | 1 | 제빵 |
| 철광산 | 곡괭이 0.1 | 철광석 1 | 1 | — |
| 대장간 | 철 1 | 곡괭이 2 | 1 | 야금 |
```
````

**카드 표**

````markdown
```cards profile="deckbuilder" 예시=참
| id | 이름 | 비용 | 종류 | 아키타입 | 키워드 | 텍스트 |
|---|---|---|---|---|---|---|
| C001 | 찌르기 | 1 | 공격 | 화력,연타 | — | 피해 6 |
| C002 | 방어구 | 1 | 스킬 | 방어 | 지속 | 방어도 5 |
```
키워드: 지속=턴이 끝나도 안 없어진다 / 소멸=쓰면 사라진다
아키타입: 화력(최소 12장) 방어(최소 12장) 연타(최소 8장)
````

### 5-3. 출력

> **C5 는 실제로 일어난다.** Factorio 가 밟았고, FFF-376 에서 이걸 고치려고
> *trigger technology*(무언가를 캐거나 만들면 해금)를 새로 넣었다고 썼다. 대형 스튜디오도 밟는 지뢰다.

### 5-5. 이 장르의 "못 올라가는 발판"

액션의 *"이 발판 못 올라간다"* 에 해당하는 것이 장르마다 있다.

| 장르 | 치명적 실수 | 잡는 검사 |
| --- | --- | --- |
| 시뮬·타이쿤 | **닭-달걀**, sink 없는 자원 | C5, C3 |
| 덱빌딩 | **자리 없는 카드** | C8, C9 |

Mega Crit(Slay the Spire) 이 한 문장으로 말해 뒀다 :

> **"Every card should have a place!"** (모든 카드는 자기 자리가 있어야 한다) — GDC 2019

카드 250장 중 어느 아키타입에도 안 끼는 카드는 **사람 눈으로 못 찾고 기계가 표를 훑으면 1초**다.

MTG 는 카드를 채우기 **전에** **설계 뼈대**(빈 슬롯 표)를 만든다. 뼈대는 **"빈칸이 어디인지" 보여주는 물건**이라,
타일맵 검증기가 "못 가는 칸"을 잡는 것과 역할이 같다. C13 이 그것이다.

### 5-6. 안 만드는 것 — 시뮬레이터

**밸런스는 스프레드시트로 한다.** 1849 방식이 그대로 베낄 만하다 —
마스터 시트에 건물별 생산·소비를 적고 도시별 순수지를 계산해서 **"숫자가 전부 0 근처면 맞은 것"**, 어긋나면 빨강/초록.

한계도 개발자가 못박았다 — *"한 번만 도는 시간제한 퀘스트는 스프레드시트로 안 된다."*
**우리 검사기도 계속 도는 정상상태까지만 노린다.**

밸런스 봇도 안 만든다. **Mega Crit 은 봇을 안 쓴다** — 사람 플레이테스터 + 자체 메트릭 + Discord 피드백 18,168건이었다.
슬라이드에 태도가 적혀 있다 : *"Don't Rely On Metrics Too Much! Data is evidence, but not a conclusion."*
게다가 봇은 **게임이 다 만들어져야** 돌아간다. 우리는 설계 단계 도구를 만드는 중이다.

| 스테이지 흐름 / 잠금-열쇠 | `flowchart` |
| 화면 흐름 | `flowchart` |
| 클래스 관계 | `classDiagram` |
| **층 구조도 / 런 구조** | `flowchart` |

| **생산 사슬 · 테크 트리** | `flowchart` (엔진 C 가 표에서 만들어 준다) |

| **아키타입 하나** (셋업 → 페이오프) | `flowchart` |

**상태 전이도는 형식 하나로 3가지 용도를 덮는다** (플레이어 이동 / 적 AI / 보스 페이즈).
**애니메이션 상태 기계는 따로 그리지 말고 이동 상태도에 합친다.**

### 지킬 것

1. **`-beta` 붙은 종류 금지** — GitHub 버전이 뒤처져 안 그려질 수 있다
2. **노드 25개 넘으면 쪼갠다** — 이게 실제로 걸리는 자리가 둘 있다
   - **층 구조도** : Slay the Spire 는 17층 × 6칸 = 102개다. **층 하나를 노드 하나로 줄이거나 막(act)별로 쪼갠다**
   - **시너지 지도** : 카드 250장은 열 배를 넘긴다. **전체 지도는 Mermaid 로 그리지 않는다.**
     진짜 자료는 `카드 × 아키타입` **행렬 표**이고, Mermaid 는 아키타입 하나를 설명할 때만 쓴다
3. **라벨은 항상 따옴표로 감싼다** — 괄호·따옴표가 들어가면 파서가 깨진다
4. 한국어 라벨을 쓴다 (도구가 폭을 계산하므로 안 깨진다)

Claude Code 터미널에서는 안 보인다. **GitHub 웹 또는 VS Code 미리보기**로 확인한다.
