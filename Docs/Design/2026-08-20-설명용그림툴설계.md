## 1. 핵심 발견 — 타일맵은 아스키 아트가 아니다

앞선 조사에서 **"LLM은 아스키 아트를 못 그린다"** 는 결론이 났다. 그런데 **타일맵은 다르다.**

| | 아스키 박스 그림 | 타일맵 |
| --- | --- | --- |
| 무엇인가 | **그림** | **2차원 배열** |
| AI가 하는 일 | 박스 크기 맞추기, 선 잇기, 라벨 넣기 | **한 줄씩 문자 찍기** |
| 1칸 틀리면 | **그림이 깨진다** | **타일 하나가 틀린다** (국소적) |
| 검증 | 사람이 눈으로 봐야 함 | **모든 줄 길이가 같은지 기계가 검사** |

즉 타일맵은 **그림이 아니라 데이터**다. 그래서 AI가 써도 안전하다.

> **3D였다면 불가능했을 것이 2D 타일 기반이라 가능하다.** 이게 이 프로젝트의 핵심 기회다.

단, **행 길이 검증기가 반드시 있어야 한다.** 이게 없으면 아스키 아트와 같은 문제가 된다.

## 3. 엔진 A — 격자·평면

### 3-1. 레벨 타일맵 (1순위)

**입력** : 문자 그리드 + 범례

````markdown
```tilemap name="1-1 첫 구간" tile=16
.....................................
.....................................
..........C..........................
.......####..........E...............
.....................####............
..P..................................
#####....######......................
#####....######...............#######
    ^^^^^^      ^^^^^^^^^^^^^^^
```
범례: P=시작 #=지형 C=수집물 E=적 ^=낭떠러지 S=체크포인트
````

**규칙**
- 한 칸 = 한 문자 = 한 타일
- **모든 줄의 길이가 같아야 한다** ← 검증기가 검사
- 범례는 그리드 바로 아래. 프로젝트 공통 기호를 `Docs/Guide/` 에 정해둔다
- 한 화면은 대략 **40×23 타일**. 그보다 크면 구간을 나눈다

**왜 이 형태인가**
- 실제 개발사(Yacht Club)가 **"오브젝트 목록 + 구간별 거친 그림"** 으로 시작한다
- *Super Mario Bros.* 분석 — **"모든 발판은 지면에서 4블록 또는 8블록 위"**. **블록 개수가 설계 언어**다
- 적 배치·체크포인트·수집물은 **별도 도면이 아니라 이 위의 주석**이다. 그래서 한 장에 다 담는다

**검증기가 할 일**
1. 모든 줄 길이가 같은가
2. 범례에 없는 문자가 있는가
3. 시작점(`P`)이 정확히 1개인가
4. (선택) 점프 기준선으로 **도달 불가능한 발판**이 있는가 ← 이게 진짜 값어치

> **4번이 이 도구의 존재 이유다.** 그림을 예쁘게 그리는 게 아니라 **"이 발판 못 올라간다"를 기계가 잡아주는 것.**

**렌더러**
문자 그리드 → 색칠된 HTML 격자. 타일 종류마다 색을 준다. 브라우저나 Artifact로 본다.

### 3-2. 이동 기준선 표 (2순위 — 표라서 서식만 정하면 끝)

| 항목 | 값 (타일) | 비고 |
| --- | --- | --- |
| 점프 최고 높이 | 4 | |
| 점프 최대 거리 | 5 | 달리기 상태 |
| 정점까지 거리 | 2.5 | `x_h` |
| 수평 속도 | 8 타일/초 | `v_x` |
| 낙하 최대 안전 높이 | 6 | |

**점프 아크 곡선은 그리지 않는다.** GDC 발표가 증명하듯 곡선은 **파라미터를 뽑기 위한 중간 과정**이고, `h` · `x_h` · `v_x` 세 값이면 곡선이 완전히 결정된다.

### 3-3. 히트박스 — 그리지 않는다

**표로만 적는다.**

| 기술 | 사거리 | 히트박스 (가로×세로) | 오프셋 | 지속 |
| --- | --- | --- | --- | --- |
| 약베기 | 1.5타일 | 24×16 px | (+12, 0) | 3F |

> **모양·위치를 그려야 하는 순간이 오면 그건 문서가 아니라 게임을 켜서 볼 일이다.**

### 3-4. UI 와이어프레임 (4순위)

첫 설계의 클래스 목록을 그대로 쓰되 **순서를 뒤로 미룬다.** 엔진 A의 격자 코드를 재활용한다.

`.wf-screen` `.wf-btn` `.wf-input` `.wf-list` `.wf-modal` `.wf-nav` `.wf-grid` `.wf-slot` `.wf-bar` `.wf-hud` 등

## 4. 엔진 B — 시간축

### 4-1. 공격 프레임 타임라인 (3순위)

**입력** : 표

```
기술: 강베기 (총 34F)
| 구간 | 프레임 |
|---|---|
| 선딜 | 1-8 |
| 판정 | 9-12 |
| 후딜 | 13-34 |
| 캔슬가능 | 21-28 |
| 무적 | 1-6 |
```

**출력** : 같은 시간축 위에 쌓인 막대

```
강베기 (34F)
  선딜     ████████··························
  판정     ········████······················
  후딜     ············██████████████████████
  캔슬가능 ····················████████······
  무적     ██████····························
```

**왜 필요한가**
- 프레임 데이터는 **격투게임 전용이 아니다.** 디자이너 글 제목이 *"**모든** 게임 디자이너가 알아야 할 프레임 데이터 패턴"* 이다
- 실제 엔진 작업이 이 형태다 — Unreal의 **Anim Notify State** 가 애니메이션 타임라인 위 **구간**으로 무기 콜리전을 켜고 끈다
- **표로는 관계가 안 보인다.** 여러 기술을 세로로 쌓아야 상호 유불리가 눈에 들어온다

**핵심** : 사람이 막대를 그리지 않는다. **표를 쓰면 도구가 막대를 만든다.**

### 4-2. 구간 페이싱 표

| 구간 | 종류 | 강도(0~5) |
| --- | --- | --- |
| 1 | 탐색 | 1 |
| 2 | 전투 | 4 |
| 3 | 휴식 | 0 |
| 4 | 전투 | 5 |

**곡선이 아니라 표다.** 실무자가 **"전용 소프트웨어는 없다"** 고 못박았고, Valve도 *Journey* 도 스프레드시트를 썼다.

같은 엔진으로 색 막대열을 뽑을 수 있다. **원칙 : 높낮이를 번갈아 배치한다.**

## 5. Mermaid 규칙 (0순위 — 만들 게 아니라 정할 것)

### 무엇에 쓰나

| 그림 | Mermaid 종류 |
| --- | --- |
| 플레이어 이동 상태도 | `stateDiagram-v2` |
| 적 AI 행동 패턴 | `stateDiagram-v2` |
| 보스 페이즈 전환 | `stateDiagram-v2` |
| 코어 루프 | `flowchart` (닫힌 순환) |
| 스테이지 흐름 / 잠금-열쇠 | `flowchart` |
| 화면 흐름 | `flowchart` |
| 클래스 관계 | `classDiagram` |

**상태 전이도는 형식 하나로 3가지 용도를 덮는다** (플레이어 이동 / 적 AI / 보스 페이즈).
**애니메이션 상태 기계는 따로 그리지 말고 이동 상태도에 합친다.**

### 지킬 것

1. **`-beta` 붙은 종류 금지** — GitHub 버전이 뒤처져 안 그려질 수 있다
2. **노드 25개 넘으면 쪼갠다**
3. **라벨은 항상 따옴표로 감싼다** — 괄호·따옴표가 들어가면 파서가 깨진다
4. 한국어 라벨을 쓴다 (도구가 폭을 계산하므로 안 깨진다)

### 확인 방법

Claude Code 터미널에서는 안 보인다. **GitHub 웹 또는 VS Code 미리보기**로 확인한다.

## 6. 안 만들 것

| 안 만들 것 | 이유 |
| --- | --- |
| **난이도 곡선 그래프** | 실무자 : **"전용 소프트웨어는 없다."** 표를 쓴다. 게다가 "매끄러운 상승 곡선"은 실무에서 부정된다 (**난이도 톱니**) |
| **점프 아크 곡선** | 파라미터 3개면 곡선이 결정된다. 가변 점프 설명 때 **1회** 필요할 뿐 |
| **정밀 히트박스 도형** | 텍스트로 불가능. 숫자 표로 대체하고 실제 모양은 게임에서 본다 |
| **콤보 트리** | 기술 5개 이하면 표로 충분 |
| **카메라 전용 도면** | 구간마다 **"region-focus + edge-snapping"** 식 **용어 라벨**을 붙이면 된다 |
| **아스키 박스 그림** | 조사에서 안 된다고 결론 났다 (타일맵은 예외 — 1장 참고) |
| **HTML → PNG 뽑기** | Playwright/Puppeteer가 필요하다. 브라우저로 보면 된다 |
| **시스템 아키텍처도** | 코드를 보면 된다. 문서로 유지하면 금방 거짓말이 된다 |

### 보류 — 곡선 그래프

두 조사가 어긋났다.

- **기획서 조사** : "숫자만 보면 밸런스 틀어진 걸 못 본다" → 만들 1순위
- **횡스크롤 조사** : 실무자 증언으로 "표로 충분" → 만들지 말 것

**실제 개발자 증언 쪽이 무거우므로 보류한다.** 다만 지적("겹쳐 봐야 보인다")도 틀리지 않으니, **실제로 아쉬워지면 그때 만든다.**

## 9. 남은 판단

- **타일 기호를 무엇으로 정할까** — `#` 지형, `.` 빈칸, `P` 시작, `E` 적, `C` 수집물, `^` 낭떠러지, `S` 체크포인트로 시작하고 부족하면 늘린다
- **도달 가능성 검사를 어디까지 할까** — 단순 점프(높이 h, 거리 x_h)만 볼지, 더블 점프·대시까지 볼지. **처음엔 단순 점프만**
- **타일맵을 Markdown 코드펜스에 넣을 때 어떤 언어 태그를 쓸까** — ` ```tilemap ` 이면 GitHub이 그냥 고정폭으로 보여준다
- 검증기를 **Node로 만들까 Python으로 만들까** — 둘 다 깔려 있다. 렌더 결과가 HTML이니 **Node 쪽이 자연스럽다**
